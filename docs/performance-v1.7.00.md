# v1.7.00：生成性能、精度与方向预加载

本轮先测原版，再改代码；仅使用已授权的三张 QA 人像、官方预览裁片和 2 秒合成视频。设备为原生 2136×3200 平板，字体 1.25；没有改显示比例或操作手机。素材只在 App 扫描范围外的 `PVG_QA_performance1700`，实际图片/视频生成器通过 ContextWrapper 将模型、缓存及写入全部限制在该目录，不启动 Activity、ViewModel、MediaStore 或真实队列。

## 格式实验

在 1280/2560 长边、四张素材上测试写入和解码，每项 3 次，另测一张 AVIF。共 62 组。统一到与生成眼图一致的不透明 sRGB；首轮保留原色彩空间的 raw 对照不可混入最终精度结论。2560 是编码负载档位，可能放大测试素材，不代表恢复更多原图细节。

下表是各组中位数再取中位数，单位 ms；不同分辨率/内容混合，仅用于本次取舍，不是通用设备排行榜。

| 格式 | 编码并写盘 | 精度检查 | 采用情况 |
| --- | ---: | --- | --- |
| JPEG 100 | 31.7 | 有损；本组最大 RGB MAE 约 0.40/255 | 保留眼图与视频中间缓存 |
| JPEG 100 + 256 KB 缓冲 | 29.0 | 与原编码眼图字节核对 | 采用 |
| PNG | 716.1 | 解码像素相同 | 手动精确导出；不是默认眼图缓存 |
| PNG + 写缓冲 | 712.7 | 解码像素相同 | 单加缓冲不足以消除编码成本 |
| WebP lossless effort 0 | 132.5 | 解码像素相同 | 比高压缩快，仍慢于 JPEG；未替换默认 |
| WebP lossless effort 40 | 202.0 | 解码像素相同 | 未采用 |
| WebP lossless effort 100 | 321.9 | 解码像素相同 | 未采用 |
| raw ARGB | 8.1 | sRGB 与像素布局一致时精确 | 1280 档 P1 约 6.55 MB；长期图片/逐帧视频存储成本大，未采用 |
| 当前 AVIF LOSSLESS | 175.2（单例） | 出现严重颜色误差 | 不作高速缓存；保存前严格校验 |

[Android 文档](https://developer.android.com/reference/android/graphics/Bitmap.CompressFormat)说明 WebP lossless 的 quality 是压缩努力，不是丢弃像素；[WebP 官方测试](https://developers.google.com/speed/webp/docs/webp_lossless_alpha_study)也区分快速与高压缩配置。公开比率不能代替当前 Android 编码器、素材和读写路径实测。JPEG 100 仍有损，不能称为完整无损缓存。

## 已采用的生成改动

1. 两张诊断深度图直接写标准 8-bit grayscale PNG，用原来的 clamp/round 规则和低压缩 zlib 流，省去全尺寸 ARGB 位图和高压缩开销。仍然是 PNG，保留原文件名、尺寸和每个诊断样本；投影继续使用原浮点深度。8 张实际模型/投影图各测 3 次，编码速度比中位数约 2.5 倍，Android 全像素一致；新增 CRC、流式分块、标准 zlib 解码及失败传播测试。
2. 图片眼图和视频帧眼图 JPEG 写入增加 256 KB 缓冲，不调低质量、不改尺寸、不修改投影。原双眼并行写入、有界视频 writer 和 complete 标记保留。
3. 视频推理会话改为按需创建：全帧缓存恢复时不校验/打开模型、不下载、不创建 GPU delegate；遇到缺失帧才创建。GPU 创建/推理/释放仍走原拥有者线程，强制 GPU 和失败传播保留，没有 CPU fallback。

## 实际生成耗时

同一台平板、同一 518/GPU、V10/50、同参数和源尺寸；这是小样本前后观察，非多设备统计。

| 项目 | 修改前 ms | 修改后 ms |
| --- | ---: | ---: |
| P1，含首个模型/原生准备 | 4890 | 4802 |
| P2，模型已在内存 | 582 | 462 |
| P3，模型已在内存 | 607 | 492 |
| 官方预览裁片，模型已在内存 | 476 | 401 |
| 2 秒/16 帧合成视频，全新生成 | 9849 | 9616 |
| 同视频，全帧缓存恢复编码 | 4573 | 404 |
| 同视频，人工移除第 8 帧 complete 后恢复 | 未作原版同条件计时 | 5091 |

热图片三项总耗时约减少 16–21%；冷视频只小幅变化，逐帧深度仍占主要时间。缓存完整短片恢复减少约 91%，主要省去约 4 秒模型准备，不能外推成长视频帧生成快 11 倍。新/旧眼图、视频 PTS、音频与输出解码另行核验，详见发布记录。

部分帧缓存缺口还存在历史时序边界：已缓存前缀不带原始深度平滑状态，单独补洞帧可能与从头连续推理不同。本次人工缺口实验已记录，不把缓存命中或时间戳一致当成每帧画面完全相同。解决它需要版本化时序 checkpoint 和独立恢复验证，本版未改时序算法或旧缓存含义。

## 自动预加载

原版按前 1、后 1、前 2、后 2 排队，固定先前一侧；尚未使用翻页方向。本版首次打开保持均衡，自动档检测捕获来源中的最近移动方向，对同向距离 d 计 2d、反向计 4d+1，当前图始终为 0。例如向后连续翻页时先后 1、后 2、前 1、前 2；反向立即重排尚未领取的任务，正在推理的图不强行中断。

只调整自动档等待顺序，不增加目标数或扩大来源。2→4→8、同档补位、最多前八后八、当前图开始推理后才放行邻图、自动暂停恢复、删除 token 均保留。固定档维持原前后均衡和不反向补位。失败、用户暂停与历史暂停项不能因方向变化被邻图自动复活；本版补上 FAILED 邻图准入检查。

这不是“最完美”或测得的真实点击概率模型。连续翻页时可减少同向等待，突然回翻可能稍慢；反向最近项仍排在前几位。没有上传浏览行为或建立私人习惯统计。需要完全均衡时可使用固定前后范围。

## 保存格式与 AVIF 精度

现有 avif-coder 2.1.4 对 sRGB 彩色样本，即使 LOSSLESS 和显式无损采样，Android 与库自身解码均出现约 34/255 RGB MAE。[对应上游实现](https://github.com/awxkee/avif-coder/blob/2.1.4/avif-coder/src/main/cpp/JniEncoder.cpp)在高质量 YUV444 转换时改用 Identity，却仍把原矩阵系数写给编码图像；这与本次颜色异常相符。仅改容器标记的实验无效，未把它作为修复分发。

“设置 → 深度与输出 → 保存到图库的格式”明确选择 PNG 或 AVIF。新增选项默认 PNG，相对当前 SBS 缓存无额外像素损失；无法还原旧 JPEG 已损失的内容。AVIF 编码后逐像素验证，失败明确报错，既不向 MediaStore 发布坏图，也不偷换 JPEG/PNG。新 AVIF 使用独立 verified 文件名，旧文件和原图保留。保存失败不再被笼统显示为“没有可保存的图”。未升级编码库或整套依赖。
